## Summary

1. **This is upstream code, not something special to this build.** The whole MCP server lives in U under `apps/server/src/mcp/` (about 19.6k lines with tests). B contains the same code: the same tool names, the `/mcp` path, `mcp_servers.t3-code`, `maxBatchThreads: 20`, and the same instructions text. B is simply about a day older. For example, `link_pull_requests` exists in U but not in B.
2. **One server, served over HTTP.** The T3 server process serves Streamable-HTTP MCP at `http://127.0.0.1:<port>/mcp` (protocol 2025-06-18), on the same HTTP server as the app. There is no separate MCP process, except a small stdio relay for ACP agents.
3. **One bearer token per agent session.** Every provider session gets a random 32-byte token. The server stores only its SHA-256 hash, mapped to a scope: environment, thread, provider session, provider instance, a capability set and a `subagent` flag. That token is the caller's whole identity. No ids travel in the URL.
4. **How the server is injected into each agent:**
   - Claude: the Agent SDK's `mcpServers: {"t3-code": {type:"http", url, headers}}` option.
   - Codex: the app-server thread config `"mcp_servers.t3-code": {url, http_headers}`.
   - ACP agents: `mcpServers` with a stdio server that is T3's own binary running `acp-mcp-bridge`. HTTP is used only for agents known to support it.
5. **A tool call becomes a typed command.** Toolkits are built with Effect's `Tool`/`Toolkit`, and every handler is wrapped by an access policy in `McpToolAccess`. Each call becomes a command such as `delegated_task.request` or `thread.stop`, sent through `ThreadManagementService.dispatch`, the same choke point the UI uses. The command id is derived from the agent's `clientRequestId`, so a retry is idempotent.
6. **There is no MCP `instructions` field.** The orchestration rules are a constant in `packages/provider-core/src/server/orchestrationInstructions.ts`. Each harness gets them a different way:
   - Claude: appended to the `claude_code` system prompt preset.
   - Codex: per-turn `additionalContext` entries, each under 4 KB, re-injected after compaction.
   - ACP: wrapped around the first user prompt.

   A test pins their size: the tool list is 47.5 KB, the Claude system-prompt append 5.2 KB.
7. **Delegation is asynchronous and wakes the parent.**
   - `delegate_task` creates a child thread whose lineage is "subagent". The child gets only the task text, prefixed with "Act as the <role> sub-agent".
   - Its mode can never be broader than the parent's.
   - When the child finishes, the server posts a message into the parent thread. The message carries up to 16 KB of result inline and starts a new turn.
   - The tool result carries `next: "Completion wakes this thread, so end your turn…"`, which tells the model not to poll.
8. **Most limits are written in the prompt, not enforced in code.**
   - "Children never spawn" and "don't poll" are instructions only.
   - Code enforces three things:
     - modes only narrow;
     - the caller must have a live run;
     - a few tools (PR watch) are hidden from subagents.
   - There is **no** enforced depth limit, child count limit, or cost/budget guard. Depth is only measured, for telemetry, capped at 5.
   - `maxBatchThreads: 20` is a limit on `create_threads`, not on delegation.
9. **The person keeps some decisions.** A parent can see a child's pending approval but cannot grant it. It can answer a child's *questions* through `t3_pending_request`. `request_secret` shows a private card and blocks until the person answers. The agent gets a one-use `secretRef` or a file path, never the value. Changing projects or environment settings needs a full-access caller.
10. **For Banda:**
    - **Copy:** the token-to-scope design, injecting per harness, mapping tool calls to the same commands the UI uses, modes that only narrow, and waking the parent with `next`.
    - **Do better:** enforce depth, child count and budget in the engine, add loop protection for thread-to-thread sends, scope reads to a project, and start with far fewer than about 70 tools.

## 1. Delivery

### Transport and which process serves it (verified)

- **Streamable HTTP MCP**, built on Effect's `McpServer.layerHttp`:
  - name `"T3 Code"`, path `/mcp`, `protocols: [McpProtocol.v2025_06_18]`, `allowSessionTermination: true`;
  - U `apps/server/src/mcp/McpHttpServer.ts:1143-1149`; B `binCli-C12fvdZY.mjs:348726`.
- It is mounted in the main server's route layer, next to the WebSocket and HTTP routes (U `apps/server/src/server.ts:742-745`). So **the T3 server process itself** (Node, inside the Electron app or headless) serves MCP. No separate MCP process runs.
- The endpoint URL is built from the server's own listening address: `http://127.0.0.1:<port>/mcp`, or the bound host (U `McpSessionRegistry.ts:86-88`).
- **ACP exception.** The ACP adapter uses a stdio relay because "ACP mandates stdio MCP support; HTTP/SSE support varies" (U `apps/server/src/mcp/AcpMcpStdioBridge.ts:13`).
  - The agent is given a stdio server whose command is T3's own executable with `acp-mcp-bridge` and `ELECTRON_RUN_AS_NODE=1`.
  - It gets the env `T3_ACP_MCP_ENDPOINT` and `T3_ACP_MCP_AUTHORIZATION`.
  - It relays JSON-RPC verbatim to the HTTP endpoint.
  - HTTP is opt-in per agent flavour, because "codex-acp 1.2.0 and pi-acp drop injected HTTP servers" (U `packages/provider-acp/src/server/adapter.ts:660-695`).
  - This matches Banda's note N §3.

### Injection per harness (verified)

| Harness | Mechanism | Where |
|---|---|---|
| Claude Code (Agent SDK) | `query()` options: `mcpServers: {"t3-code": {type:"http", url, headers:{Authorization}, timeout: 65 min}}`, plus `allowedTools: ["mcp__t3-code__*"]` (in a read-only sandbox, only the read-only tools listed) | U `apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts:1694-1744`; B `:197851` |
| Codex (app-server JSON-RPC) | thread config key `"mcp_servers.t3-code": {url, tool_timeout_sec: 3900, http_headers:{Authorization}}`. The comment says "Override only T3's server so launch-argument MCP servers survive." It also sets `mcp_optional_startup_grace_ms: 10000`. | U `Adapters/CodexAdapterV2.ts:1328-1365`; B `:228943` |
| ACP agents | `session/new` `mcpServers` with the stdio bridge above. An HTTP entry is added only when the flavour supports it. | U `packages/provider-acp/src/server/adapter.ts:660-695` |
| Others (OpenCode, Cursor, Muse, Pi) | headers in each provider's own MCP config | U `packages/provider-opencode/src/server/adapter.ts:973`, `provider-cursor/.../adapter.ts:213`, `provider-pi/.../mcpInjection.ts:305` |

The timeouts are long on purpose. `t3_thread_wait` and `delegate_task mode:"wait"` can block for up to 60 minutes (U `ClaudeAdapterV2.ts:1711-1712`, `OrchestratorMcpService.ts:126`).

### Per session or shared? (verified)

- **The server is shared. Credentials are per session.** `ProviderSessionManager.prepareMcpSession` runs once per thread, serialised per thread by a lock (U `apps/server/src/orchestration-v2/ProviderSessionManager.ts:441-503`). It does the following:
  - works out the capabilities: `orchestration`, `worktree` and `pull-requests` always; `preview` if the user allows the browser; `device` if devices are allowed;
  - reads whether the thread's lineage is `subagent`;
  - **reuses** the existing token if it still resolves to the same thread, provider instance, capabilities and subagent flag ("Live providers build MCP clients once; reuse credentials across workspace handoffs");
  - otherwise revokes the thread's old tokens and issues a new one.
- The registry is **in memory** (`SynchronizedRef`), so a server restart drops every token (U `McpSessionRegistry.ts:84`). *Inferred:* sessions get new tokens when they are next prepared.

## 2. Identity and auth

### What identifies the caller (verified)

- **Only the bearer token.**
  - `McpSessionRegistry.issue` creates a `providerSessionId` (UUID) and 32 random bytes as base64url. It stores `sha256(token) → scope` and returns `authorizationHeader: "Bearer <token>"` (U `apps/server/src/mcp/McpSessionRegistry.ts:95-138`).
  - The scope type is `McpInvocationScope` (U `McpInvocationContext.ts:100-108`), with these fields:
    - `environmentId`
    - `thread: {threadId, providerSessionId, providerInstanceId, subagent}`
    - `capabilities`
    - `requestNamespace`
    - `issuedAt`
    - `client` (for outside OAuth clients)
    - `linkedEnvironments`
- The **project** is not in the token. It is looked up from the thread (`resolveProjectId`, U `threadAccess.ts:157-168`).
- The **parent** is not in the token either. It comes from the thread's lineage in the projection store (`relationshipToParent`, U `ProviderSessionManager.ts:459-462`).
- There are no ids in the URL and no env vars, except the ACP relay env above.

### How a request is authorised (verified)

1. The auth middleware reads `Authorization: Bearer …` and looks the token up in the registry (`registry.resolve(token)`). If that fails, it tries the OAuth client authenticator, which serves outside MCP clients and linked machines (U `McpHttpServer.ts:195-237`).
2. If neither matches, it returns 401 with `WWW-Authenticate`. Launched agents are never offered OAuth: "Launched agents cannot open OAuth browsers; OAuth would mint credentials outliving their session" (U `McpHttpServer.ts:86-121`).
3. **Liveness:** a token stops working after 24 hours idle, and each successful call refreshes it ("`/mcp` is outside environment auth, so idle tokens stop authenticating", U `McpSessionRegistry.ts:59-64`). `RunExecutionService` also refreshes the token on run activity (`touchActiveMcpThread`, U `RunExecutionService.ts:1634`).
4. The resolved scope is provided to each request as the Effect service `McpInvocationContext`, so every handler knows who is calling.
5. Each handler is wrapped in an **access policy** from `McpToolAccess.ts` (`reads`, `readsAsCaller`, `actsAsCaller`, `writes`, `writesThreads`, `startsThreads`, `writesEnvironment`). A lint rule (`t3code/no-raw-mcp-registration`) stops tools from being registered any other way (U `McpToolAccess.ts:71`). The policies enforce:
   - capability checks (`requireMcpCapability`, U `McpInvocationContext.ts:166-175`);
   - **live caller**: a thread caller must own an active run, or a background subagent, in an unarchived thread, and stale credentials cannot write to *other* threads (U `threadAccess.ts:123-150`, `OrchestratorMcpService.ts:1185-1229`);
   - **mode ceiling**: the target's runtime and interaction modes may not be broader than the caller's (U `threadAccess.ts:114-121`, `delegatedTaskModes.ts:36-73`);
   - **full access** for changing projects or environment settings ("needs a live full-access/default calling thread or a full-access client", U `McpToolAccess.ts:283-318`, `threadAccess.ts:152-155`).
6. **Outside clients and other machines** use OAuth. They carry an access level (`read-only` up to `full-access`). They may send `T3-Mode-Limit: <runtime>/<interaction>` to narrow, never widen, their own limits. Linked machines use this to pass on the limits of the agent calling for them (U `McpInvocationContext.ts:51-97`, `McpHttpServer.ts:152-183`, `peer/PeerMcpClient.ts:29-33,161`).

### Gaps I noticed (verified from code, judgement mine)

- **Reads are not scoped to a project.** `loadTargetThread` and `readThread` check only that the thread exists and is not deleted (U `OrchestratorMcpService.ts:1154-1170`, `threadAccess.ts:170-205`). Any agent with the `orchestration` capability can therefore read any thread in the environment.
- **On ACP, the agent's shell can see the token.** `T3_ACP_MCP_AUTHORIZATION` is placed in the agent's process environment on purpose, as a fallback "call them through the terminal" (U `orchestrationInstructions.ts:66-67`). Any shell command the agent runs can then call `/mcp` directly.

## 3. Architecture

### Where the MCP layer sits (verified structure; layering words are mine)

```
Agent (Claude SDK / Codex app-server / ACP)
   │  HTTP POST /mcp  (Bearer token)
   ▼
McpHttpServer        auth middleware → McpInvocationContext (per request)
   │                 toolkits: orchestrator, thread, project, worktree, preview,
   │                 previewControls, html, device, attachment, pullRequests, environment
   ▼
McpToolAccess        access policy wrapping each handler; linked-env routing
   ▼
*McpService          OrchestratorMcpService (3,258 lines), WorktreeMcpService, ThreadMetadataMcpService
   ▼
ThreadManagementService.dispatch(command)      ← the same choke point the UI/WebSocket uses
   ▼
Orchestrator (orchestration-v2/Orchestrator.ts, 14,018 lines)
   → domain events (EventStore) → ProjectionStore (read model) → EffectOutbox/EffectWorker
   → ProviderSessionManager → Adapters (Claude/Codex/ACP…) → agent processes
```

- **Commands.** Examples: `delegated_task.request`, `delegated_task.wake-policy`, `subagent.stop`, `thread.stop`, `thread.create`, `message.dispatch`, `secret_request.record` (U `OrchestratorMcpService.ts:2401, 1668, 2666, 2587, 2791, 2121`; `Orchestrator.ts:551-557`).
- **Events.** `dispatch` returns `storedEvents`. The MCP service reads the result back from them, for example the `subagent.updated` event that carries the new `taskId` (U `OrchestratorMcpService.ts:2431-2442`).
- **Read model.** Tools read projections through `threadManagement.getThreadRecords(...)` and `getProjectThreadRecords(...)`, for example `["runs","subagents","contextTransfers"]`.

### How a tool call becomes a command (verified example: `delegate_task`)

`OrchestratorMcpService.delegateTask` (U `:2304-2500`) works in this order:

1. Resolve the caller's thread and its projection. It requires an **active parent run owned by this provider session**, or it fails with `parent_not_active`.
2. Derive a stable `commandId` from the caller scope, the `clientRequestId` and the operation (`stableCommandId`). Check `hasReceipt(commandId)`, so a retry replays the original result instead of starting a second child.
3. Resolve the target provider and model. If the provider looks unavailable, it re-probes once.
4. Resolve the modes. A child may not be broader than its parent.
5. For `isolation:"worktree"`, resolve the parent's `HEAD` commit to be the child checkout's base.
6. `dispatch({type:"delegated_task.request", parentThreadId, parentRunId, parentNodeId, task, modelSelection, runtimeMode, interactionMode, workspaceStrategy, completionWake})`.
7. Find the task and child thread in the stored events, prepare the child's worktree run, then return `readTask(...)`. With `mode:"wait"`, it blocks first.

### One registry? Where descriptions come from (verified)

- Each toolkit is a `Toolkit.make(...)` of `Tool.make(name, {description, parameters, success, failure, dependencies})`, with annotations such as `Title`, `Readonly`, `Destructive`, `Idempotent` and `OpenWorld` (for example U `toolkits/orchestrator/tools.ts`).
- `McpHttpServer.layerTools` merges all eleven toolkits into **one server** (U `McpHttpServer.ts:1152-1164`). The comment says: "Every tool the T3 MCP server advertises. AgentContextBudget.test.ts measures this set."
- **Descriptions** are short, hand-written strings in each `tools.ts`. Parameter docs come from schema annotations in `packages/contracts/src/orchestratorMcp.ts`. One example is the `runtimeMode` text "…Above yours is rejected." (U `:189-194`).
- **Advertised schemas are compacted.** `advertisedJsonSchema` merges tagged unions, drops `null` branches and drops JSON-string fallbacks, so agents see a smaller schema than the full codec (U `McpHttpServer.ts:1013-1037`, `advertisedJsonSchema.ts`).
- **A size budget is enforced by a test.** `apps/server/src/provider/agentContextBudget.json`: `mcpToolListJsonBytes: 47538`, `claudeSystemAppendBytes: 5153`, `codexAdditionalContextBytes: 6883`.
- Tool counts: U defines 70 `Tool.make` tools. The agent in this session sees a similar set from B.

### Deferral and progressive disclosure (verified)

- **The harness does the deferring, not T3.** Claude Code defers MCP tools behind its own ToolSearch. T3 forces `ENABLE_TOOL_SEARCH=true` when the user's setting is `auto` or `auto:N`, because "auto tool search sends every MCP schema in full while they fit under a share of the context window, which T3's tools do on 1M models" (U `ClaudeAdapterV2.ts:1414-1425`, `:1539`).
- T3 then tells the model about it in the prompt:
  - "T3 MCP tools are deferred: load one with ToolSearch before you call it" (U `ClaudeAdapterV2.ts:1445-1450`);
  - "T3 tools may load late. Try the name once before you call it absent" (`orchestrationInstructions.ts:20`).
- **T3's own disclosure works in three ways:**
  1. **Capabilities per credential.** The `preview` and `device` tools fail, and their instructions are left out, when the user withholds them (`browserToolsAvailable`, `toolInstructions`, U `CodexDeveloperInstructions.ts:23-31`).
  2. **`McpSchema.EnabledWhen` per caller.** `hiddenFromSubagents` hides `watch_pull_request` and `unwatch_pull_request` from children. `hiddenWhileLinksOff` hides `t3_environment_links`, `t3_environment_link` and `t3_environment_unlink` while the Labs flag is off (U `McpInvocationContext.ts:130-146`, `toolkits/pullRequests/tools.ts:398,412`, `toolkits/orchestrator/tools.ts:320,334,348`).
  3. **Results as the next step.** Results carry the next step: `next`, `link`, `nextPosition` and `nextTextOffset` for paging, and recovery text inside errors.

## 4. Agent to agent

### How `delegate_task` creates a child (verified)

- The Orchestrator handler (U `Orchestrator.ts:7481-7610`) does the following:
  - checks again that the parent run is active, is not stopping, and owns the parent node;
  - derives deterministic ids for the child thread, message and task node from the `commandId`;
  - builds a child thread with `makeSubagentChildThread` (lineage `subagent`), carrying the requested model and modes;
  - records an `OrchestrationV2Subagent` with `origin:"app_owned"`, `status:"running"` and `completionWake`;
  - records an execution node of kind `subagent` under the parent run.
- **The child sees only the task.** The tool description says "No parent history" (U `toolkits/orchestrator/tools.ts:88`). `taskPrompt` adds `"Act as the <role> sub-agent for this task.\n\n"` when a role is given (U `delegatedTaskModes.ts:90-95`).
- *Observed in this session:* this sub-agent's own task began with exactly "Act as the research sub-agent for this task."
- The child gets its own MCP token with `subagent: true` (U `ProviderSessionManager.ts:459-499`).

### How the parent learns the child finished (verified)

- **`async` (the default).** The task gets `completionWake: "always"` (U `OrchestratorMcpService.ts:2414-2418`). While running, the tool result includes `next = "Completion wakes this thread, so end your turn. Do not wait on it or poll it."` (U `packages/contracts/src/orchestratorMcp.ts:199-201, 239`).
- **The wake.**
  - When the child reaches a terminal state, the Orchestrator's delegated-completion delivery claims every pending terminal task of that parent run and allocates a message in the parent thread (U `Orchestrator.ts:12740-12830`).
  - The message text inlines each result up to `DELEGATED_RESULT_INLINE_BYTES = 16_000` total. Anything larger becomes "Use task_status with taskId … to read the result" (U `Orchestrator.ts:693-714`; fallback text in `ProviderContinuationService.ts:13-18`).
  - Delivery is generation-numbered and acknowledged (`delegated_task.completion-delivery.acknowledge/dispose`), so a restart neither loses nor duplicates it.
- **`wait`.** The call blocks for up to `timeoutMs` (default 10 minutes, maximum 60) (U `OrchestratorMcpService.ts:125-126, 2475-2482`).
  - A question or approval ends the wait early (`pendingApproval` and `hasPendingQuestion` in the result, U `contracts/src/orchestratorMcp.ts:227-235`).
  - On timeout the child keeps running. The server upgrades the task to `completionWake:"always"`, so a later finish still wakes the parent (U `OrchestratorMcpService.ts:2484-2500`).
- **Questions from children.** `DelegatedTaskQuestionReactor` posts a message into the parent: "Delegated task … asked a question … Read it with t3_pending_request … Answer it … when the answer follows from the task or the user's instructions; otherwise ask the user" (U `orchestration-v2/DelegatedTaskQuestionReactor.ts:32-62`).
- **`task_status`** reads the task, with `workState: working | waiting_for_children | result_available`. Reading the summary marks it delivered. Its description says not to call it before the wake (U `toolkits/orchestrator/tools.ts:99-111`).
- **`t3_thread_wait`** waits for any thread's run. On timeout it returns a `next` that tells the agent to end its turn (U `toolkits/orchestrator/tools.ts:282-294`).

### Cancellation (verified)

- `task_cancel`: "Stops its running and queued turns, its delegates, and its PR watches, including later runs in its child thread. A finished task keeps its result" (U `toolkits/orchestrator/tools.ts:113-124`).
- The implementation walks the task's children, dispatches `thread.stop` on them, then `subagent.stop` on the task (U `OrchestratorMcpService.ts:2507-2690`).
- The rules tell agents to use `task_cancel`, never `t3_thread_interrupt`, on a child. Interrupt also refuses delegates ("For a delegate, use `task_cancel`", U `tools.ts:300`).

### Limits (verified; "prompt only" means no code check found)

### Cross-provider delegation (verified)

- `orchestrator_capabilities` lists providers, models, options and runtime modes, with `canRunChildTask` and `canRunCrossProviderChildTask` and the reasons any are blocked (not installed, not authenticated, disabled) (U `OrchestratorMcpService.ts:2228-2302, 345-365`).
- `target.providerInstanceId`, `model` and `options` pick another harness. The child thread then simply runs on that provider's adapter (`providerAdapters.get(command.modelSelection.instanceId)`, U `Orchestrator.ts:7534`).
- The prompt decides when to use native subagents and when to use `delegate_task`: native only for the same provider and settings, finishing within this turn (U `orchestrationInstructions.ts:9`).
- **Other machines:** `target.environmentId` sends the task to a linked machine through `RemoteDelegation` and `PeerMcpClient`, which calls that machine's `/mcp` with OAuth plus `T3-Mode-Limit` (U `OrchestratorMcpService.ts:2305-2320`, `peer/PeerMcpClient.ts:29-33`). This is behind a Labs flag ("Linked environments beta").

### `t3_thread_send` between arbitrary threads, and loops (verified)

- `sendToThread` (U `OrchestratorMcpService.ts:3055-3103`) does the following:
  - loads any thread by id;
  - for a thread other than the caller's own, requires a live caller run;
  - requires that the target's modes are not broader than the caller's ("The target cannot run with broader modes than yours");
  - dispatches through `threadManagement.sendToThread` with `senderThreadId`, `mode: auto|queue|steer|restart`, and an idempotent `commandId` and `messageId`.
- A send to a *finished child* starts a fresh delegated task and returns its `taskId` (tool text, U `tools.ts:271-272`).
- **Loop protection: none found in code.** No hop count, no rate limit, no ping-pong check. `senderThreadId` is only carried through as metadata (U `ProviderTurnStartService.ts:1677`). What limits loops is the prompt ("Every new delegate review or re-check is a new `delegate_task` … never a `t3_thread_send`", `orchestrationInstructions.ts:11`), the live-run requirement, and the user. *Inferred:* two full-access agents could keep each other busy.

## 5. Human in the loop

All verified unless marked.

- **Approvals stay with the person.**
  - A parent sees `pendingApproval` in the task result, described as "Grants no approval rights" (U `contracts/src/orchestratorMcp.ts:231-235`).
  - `t3_pending_request` can list, read and answer *questions*. Its description says it "cannot approve a permission request", and approvals are not listed (U `toolkits/thread/tools.ts:127-140`).
  - The human approves in the UI. Narrow child modes "pause for human approval, not read-only" (contracts `:189-194`).
- **Questions.** A child's question wakes the parent, which should answer only "when the answer follows from the task or the user's instructions; otherwise ask the user" (U `DelegatedTaskQuestionReactor.ts:41-46`). This is a prompt rule; the parent *can* answer.
- **`request_secret`** (U `OrchestratorMcpService.ts:2097-2227`; tool text `tools.ts:198-209`):
  - It records a `secret_request` turn item, which shows as a private card.
  - It **blocks the call**, polling until the person saves or declines, the run ends, or it times out (default 10 minutes, maximum 60). On timeout or abort it closes the card as cancelled.
  - It returns `status` plus a one-use `secretRef`, or with `delivery:"file"` a private file path. "You never see the value."
  - It requires an active run owned by this session.
- **Linking another machine.** `t3_environment_link` shows a card. The result comes back later as a message, and the agent must "never ask for a pairing code in chat" (U `toolkits/orchestrator/tools.ts:322-334`).
- **What an agent may do alone, within its own modes:**
  - delegate and cancel its children;
  - read any thread;
  - send to any thread no broader than itself;
  - create and launch top-level threads (no broader than itself);
  - schedule tasks: `schedule_task` runs "with no turn active", with modes capped by the caller's (U `OrchestratorMcpService.ts:1940-1955`);
  - link and watch PRs;
  - drive the shared browser preview, if allowed.

  Changing projects or environment settings needs a full-access/default caller (U `McpToolAccess.ts:283-318`).
- **Claude pre-approval.** T3 adds `allowedTools: ["mcp__t3-code__*"]`, so T3 tools never prompt in Claude's own permission UI. In a read-only sandbox, only the read-only tools are pre-approved (U `ClaudeAdapterV2.ts:1690-1734`). *Inferred:* T3 relies on its own server-side mode checks instead of Claude's prompts.

## 6. Instructions

All verified unless marked.

- **The source is one TypeScript module**, `packages/provider-core/src/server/orchestrationInstructions.ts`. It holds:
  - `T3_CODE_ORCHESTRATION_SECTIONS`, three sections, each kept under 4,000 bytes because "Codex truncates entries over 4,000 bytes";
  - browser and device sections, plus ACP-only mode and fallback text.
- A second module, `runtimeInstructions.ts`, adds `<runtime_info>` and `<pull_request_linking>`.
- There is **no MCP `instructions` field**: `layerHttp` is given only name, version, path and protocols (U `McpHttpServer.ts:1143-1149`), and no `instructions` appears anywhere in `apps/server/src/mcp`.

**How each harness gets the text:**

- **Claude:** `systemPrompt: {type:"preset", preset:"claude_code", append: runtimeInstructions + ORCHESTRATION + CLAUDE_BACKGROUND_WAIT (+ device)}`, set once at session start (U `ClaudeAdapterV2.ts:1588-1601`). Claude-only additions include the ToolSearch hint. A `SubagentStart` hook passes device rules to native subagents.
- **Codex:** `buildCodexAdditionalContext`. Each section becomes an `additionalContext` entry (`t3_code_orchestration_01..03`, `t3_code_runtime`, `t3_code_tools`) on **every `turn/start`** (U `CodexDeveloperInstructions.ts:40-60`, `CodexAdapterV2.ts:777-794`). The comment says: "Keep this outside collaboration mode; model-catalog mode text overrides client developer_instructions". Because "Codex drops client developer messages during compaction but only resends additionalContext when it changes", T3 re-injects the entries after compaction with `thread/inject_items` (U `CodexAdapterV2.ts:1680-1690`).
- **ACP and Cursor (prompt-based):** `t3AcpPromptWithInstructions` and `t3OrchestrationPrompt` wrap the user prompt in `<t3_code_instructions>…</t3_code_instructions><user_request>…</user_request>`. This happens on the first prompt and again whenever the mode or tool availability changes (U `orchestrationInstructions.ts:77-134`).
- **OpenCode:** a system prompt (`t3OrchestrationSystemPrompt`).

**How the text is kept current:**

- It ships in code. There is no fetch at run time.
- The byte budget test (`agentContextBudget.json`) and adapter tests pin it.
- *Observed:* this session's own system prompt carries B's older wording, "One link_pull_request per PR", while U now says "link_pull_request, or link_pull_requests for several". The text changes with each release. B contains the same sections (`binCli-C12fvdZY.mjs:173043`).

## 7. Lessons for Banda

Context from N: Banda's engine is Rust. It talks to Codex app-server natively, uses ACP for the rest, and plans the Claude Agent SDK and native adapters later.

### Copy

1. **One MCP endpoint in the engine, with one token per session that maps to a scope.**
   - Store only a hash of each token.
   - The scope holds thread, provider session, capabilities and subagent flag.
   - Reuse the token across workspace hand-offs, and revoke it when the session stops.
   - Why: identity cannot be forged by an id in the URL, and one process owns state and auth.
2. **Inject per harness, and keep a stdio relay.**
   - Codex: `mcp_servers.<name>` in thread config.
   - Claude SDK: `mcpServers` with `type: http`.
   - ACP: `session/new mcpServers` with a stdio bridge that is Banda's own binary relaying to HTTP.
   - Why: ACP requires stdio, and some ACP agents drop HTTP servers (U `provider-acp/.../adapter.ts:660`).
   - Set long tool timeouts (more than 60 minutes) if any tool blocks.
3. **Turn tool calls into the same commands the UI sends, with idempotency keys.** `clientRequestId` gives a stable `commandId` plus receipts. Why: one choke point for checks, replay-safe retries, and an event log that records what agents did. This fits Banda's ADR 0002 (engine writes and keeps the work).
4. **Modes that only narrow,** checked on every write: delegate, send, launch, schedule. Pass the limit on across machines in a header. It is simple, and the code enforces it.
5. **Asynchronous delegation that wakes the parent,** never polling.
   - When the child finishes, post a message into the parent that carries the result inline up to a cap.
   - Add `next` to results that are still running.
   - Number and acknowledge deliveries so a restart is safe.
   - Why: polling wastes turns and tokens, and models obey a `next` in the result better than a rule in the system prompt (*inferred*).
6. **Keep the agent's context small.** Short descriptions, compacted schemas, capability-gated tools and instructions, `EnabledWhen` per caller, and **a test that pins the byte size** of tools plus instructions.
7. **Write the instructions once and deliver them per harness.** Keep sections under 4 KB, re-inject after compaction, and drop instructions for tools that are unavailable.
8. **Keep the person's powers with the person.** A parent may see an approval but not grant it. Secrets go through a card and a one-use ref, never through chat.

### Avoid, or do better

1. **Enforce limits in the engine, not in prompts.** T3 has no enforced depth limit, child count limit, budget or "children never spawn" rule. Banda should have:
   - a depth cap;
   - a cap on live children per parent and per environment;
   - a spend or turn budget passed down to children;
   - a refusal of `delegate` when the caller is a subagent and its task did not allow it.
2. **Add loop protection to `thread_send`.** A hop count or causal chain carried in `senderThreadId`, a rate limit per pair of threads, and a refusal to wake the sender.
3. **Scope reads.** T3 lets any orchestration-capable thread read every thread in the environment. Banda should default to the same project or the same lineage, with wider reads only by grant.
4. **Keep tokens away from the agent's shell when possible.** T3 puts the ACP token in env on purpose. If Banda needs a terminal fallback, give it a separate, narrower credential.
5. **Do not copy the size.** T3 has 70 tools, a 3,258-line MCP service and a 14,018-line Orchestrator. Start with about 8 tools: capabilities, delegate, task status, task cancel, thread read, thread send, request secret, pending request.
6. **Avoid instructions tied to one harness** where possible. T3's rules name `Agent`, `spawn_agent`, `ScheduleWakeup` and `Monitor`, and must follow each harness's releases.

### Unfinished or fragile in T3

All verified unless marked.

- **Linked environments** are a Labs beta. The tools are hidden and calls refused while it is off (U `McpHttpServer.ts:185-192`).
- **Harness-specific workarounds**, each of which can break with a harness upgrade:
  - Claude's ToolSearch override, which copies Claude Code 2.1.310's own integer parsing of `auto:N` (U `ClaudeAdapterV2.ts:1426-1441`);
  - Codex additionalContext caps and loss on compaction;
  - OpenCode sending JSON-string unions (contracts `:58`);
  - codex-acp and pi-acp dropping HTTP MCP servers;
  - `t3_background_wait`, which works with Claude only.
- **Change is fast.** U was 183 commits ahead of the installed build after about a day, and tools are being added (`link_pull_requests`). Expect names and texts to move. Pin a commit when you borrow ideas.
- **Tokens live in memory with a 24-hour idle window.** A restart drops every token. A leaked token works for up to a day while it is used (*inferred* risk).
- **Approvals cannot be delegated.** A long tree of supervised children waits on the person. That is a design choice, but Banda should design how one person handles approvals for many children.
