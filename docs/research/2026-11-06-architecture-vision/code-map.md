##### Kernel and engine binary (kernel/src, engine/src, contract/, CLI: banda serve/call/follow/mcp)
SUMMARY: The kernel (kernel/src, about 7.6k LOC with in-file tests) is a library. The `banda` binary assembles it in engine/src/serve.rs with 11 compiled-in modules and serves it over one WebSocket on 127.0.0.1. The first frame of a connection must be `hello`. Its token resolves to a Caller{participant, only} in one of two ways: through the Identity port (the per-run owner secret) or, as a fallback, through the in-memory pass table for Agents. Kernel::call then routes by string prefix. `window.*` goes to the window road. `projects.*` goes to the kernel's own handlers, which skip the event log and receipts. `<module>.*` goes to the module, after `place()` picks the Project or the machine scope and draws a Wall for pass holders. For module methods the kernel looks up an earlier receipt, runs access::decide (Participant kind × a 5-value Right), and gives an allowed `Call` to the dispatch generated by methods!, which decodes the params and runs the handler. Once-only behaviour is opt-in: a handler must wrap its write in Call::command. That runs a closure on the Project's single writer thread, in one IMMEDIATE transaction with the receipt, the events (Tx::emit) and the outbox rows (Tx::enqueue). Events are broadcast only after commit, and the commit wakes the outbox worker. The outbox runs effects in order per (module, key), retries with backoff, settles in the module's own transaction, and recovers effects claimed under an earlier boot. Subscriptions replay the log a page at a time and then switch to live events with no gap or repeat (Heard). Streams are untyped tokio mpsc channels, forwarded with one piece in flight. The methods! table is the one declaration of each method's kind, params, answer, Right and tool flag. ts-rs writes TypeScript into contract/src/generated when `cargo test` runs, CI fails on drift, and contract/src/methods.ts joins the module maps by hand into one closed `Methods` type. There are only two scopes. Project is a folder plus its own SQLite under projects/<id>. Machine is a fake Project at state/machine that holds workspaces, harnesses, keys, problems and sharing. The CLI finds the engine through a file on the local disk and speaks the same frames. `banda mcp` is a stdio MCP-to-WebSocket pipe that offers the tool-marked methods under an Agent pass. The core (store, receipts, outbox, Heard, frames) is genuinely deep. The host API that modules see around it is wide and leaky: raw rusqlite, host paths, tokio channels and closures. Idempotency and effect discipline are conventions in each handler. Access is coarse and has no capabilities. The single-host assumptions are each small and visible. The hardest blockers are two: the window road is used as an RPC for host work, and the Module trait is in-process Rust that cannot become a WIT world as it stands.
STRENGTHS: The store is a deep module: a single writer thread, events published only after commit, and receipts committed in the same transaction as the change. | Command receipts detect an ID reused for another method or author, and refusals become the command's answer too. | The outbox is complete and small to use: order per (module, key), parallel across keys, backoff, a panic counts as a failure, the end of a run is recorded until it commits, and recovery after a restart is replay-or-abandon chosen by the module. | Subscriptions have no gap and no repeat: the subscriber listens before it reads, falls back to the log on lag, and the TS client resumes from the last seq after a reconnect. | The event log is append-only, enforced by triggers. | methods! is one declaration per method that yields the Right, dispatch, TS types, tool JSON Schema and the `banda modules` listing. CI fails when the generated contract drifts. | Stable refusal codes, including may_have_run, keep engine failures apart from refusals. Callers act on `code`. | Backpressure on streams: one piece in flight, so a slow window slows the module down instead of filling memory. | The CLI is Unix-shaped: JSON in, JSON out, NDJSON for follow, exit codes 0/1/2, and a printed `--command <id>` for a safe retry when a connection is cut. | `banda mcp` is a clean pipe from stdio MCP to the same API, with tools taken from the methods tables, not a second implementation. | The kernel names no module, and a test enforces that. | The single-host assumptions are each small and in one place: host constant, Identity port, PROTOCOL, owner, per-Project owner in access::decide. The seams already exist.
WEAK:
- [high] The host API leaks its implementation: raw rusqlite connections, host paths, tokio channels and Rust closures. Table ownership is enforced by grepping source, and any module can read every table, kernel_receipts included, or DROP the log's triggers. (kernel/src/store.rs:94-96 (Tx::sql), 170 (reader only query_only); kernel/src/project.rs:7) → Put a SQLite authorizer (rusqlite authorizer hook) on the writer and reader connections, keyed on the calling module's table prefix, and expose the log only through the API. Define the host API as data (statements and params in, rows out; events and effects as values) so the same contract can be bound to Rust and to WIT.
- [high] Idempotency and the outbox are conventions in each handler, not something the kernel guarantees. A `command` only has to carry an ID. Handlers are expressly allowed to act before they write, and files.write, rename and trash do disk IO inline with no receipt, no event and no outbox. (kernel/src/methods.rs:287-297 (@check command only requires an ID); kernel/src/module.rs:1) → Have the kernel store a success receipt for every `command`, whether or not the handler used Call::command. Split handlers into a pure decide step (inside the transaction: the future WASM handler) and effects queued to the outbox (the future worker). Reclassify inline-IO methods as honest `call`s, or move their IO into effects.
- [high] The window road has one holder (the latest window to ask wins) and serves as an RPC for host work. Agents' browser tools, Claude usage scans and sharing's posting run in, or wait for, whichever client holds it. (kernel/src/window.rs:10-12, 135-140, 28-46 (no device in WindowRequest); modules/browser/e) → Turn it into a device road: sessions register a device ID and its capabilities, ask_window takes a target (a named device, wherever the Person is, or a host worker), and requests route per device. (kernel/src/access.rs:31-48) → Replace decide(Participant, Right, owner) with decide(Session{participant, app?, device?, scopes}, Capability, Project). ##### Decided architecture in documents (architecture.md, GLOSSARY, ADRs 0001/0005/0014/0022/0025/0028/0029/0032/0040/0056/0059/0065/0069/0071/0080/0081, draft 0062, open ADR PRs #460 and #385, research notes)
SUMMARY: Citations: draft ADR 0062 is cited as "0062(draft):N", meaning PR #557: docs/adr/0062-banda-is-a-kernel-a-platform-and-apps-built-on-one-sdk.md. PR ADRs are cited by the file in the PR diff. Everything else is relative to the arch-review worktree.

What is built and accepted is a single-machine design. One Rust engine owns the work. It runs a small kernel: the Project store, an append-only log, the command path (receipt, events, view tables and outbox written in one transaction), access, identity, passes, the registry and the API. Its modules are crates compiled into one binary, each with a `methods!` table that generates the method's right, its dispatch, its TypeScript types and its Agent tools (architecture.md:31-33, 172-203; ADR 0014). Modules are either Project-scoped or machine-scoped (workspaces, harnesses, keys). A machine module may never hear a Project's log; the only exception lets numbers through, via `tally` (ADR 0040:54; kernel/src/project.rs:856-860).

The window is an Electron client: React Panes get a live `Engine` object, and `window.banda` is one bridge table. The window is still the parent of the engine (architecture.md:809-823, 976-984). Several jobs that sound like engine work actually run in the client: working out who calls the Person, the seen marks, `done` sequences, the browser's waits, Visuals and media, and settings writes.

Draft 0062 rewraps this as three layers and three places. The layers are kernel, platform and Apps, with the SDK as the border between platform and Apps. The places are the host, the client view and the device. An App's host logic is WASM handlers that run inside the kernel's transaction, plus worker processes. Capabilities are declared in the manifest, Apps reach each other through intents, and an App's UI is a shadcn tree rendered on the host and drawn by the client. ADR 0081 adds several hosts: one writer per record, Ed25519 pairing, transport over iroh, attention worked out on the host, and a range of protocol versions. ADR 0080 adds themes resolved on the device from tokens.

The direction is coherent and borrows good precedents: Zed and Zellij for WASM, Raycast for remote rendering, T3 Connect for host-signed sessions. But the documents were written as overlays and never reconciled. 0062 has no Changes section, yet it reverses ADR 0005 decisions 12-13, ADR 0029 decision 1 and ADR 0040 decision 3, and it supersedes PR #385. ADR 0081 is accepted while it rests on the proposed 0062 and on the open PR #460, whose number (0049) collides with an ADR already on main.

The biggest structural gap: the kernel has only a Project scope and a machine scope. Yet 0081 needs a Person scope (the arrangement, themes, keys, seen marks) and host-wide projections over the Project logs (the Inbox, placing an Agent's Panes from other hosts). Both break the one-way wall the kernel enforces today.

Five more things are only sketched: the unit of work across scopes and hosts, how contracts are versioned, the data lifecycle, how fast the tiling responds against a remote home host, and the host-client protocol.
STRENGTHS: One unit of work inside a scope is precise and deep: receipt, events, view tables and outbox commit together.
