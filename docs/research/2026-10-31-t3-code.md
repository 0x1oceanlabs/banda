`apps/server/src/orchestration-v2/testkit/fixtures/` holds 89 scenarios.
Each one is a folder with an input, the raw transcript of each Harness as
NDJSON (`<harness>_transcript.ndjson`) and the expected output.

| Harness | Transcripts |
|---|---|
| Claude | 39 |
| Codex | 27 |
| OpenCode | 21 |
| Grok | 16 |
| ACP Registry agents | 11 |
| Cursor | 11 |
| Fx | 9 |
| Muse | 8 |

**What the scenarios cover**, by folder name:

- background subagents and tasks, with their wake-ups;
- compaction after a peer turn or a resume;
- resume after a restart, and interrupts;
- queued prompts, plans, todos and skills;
- MCP tool presentation, web search, command output streaming;
- malformed input, and an ACP elicitation.

**How they use them:** `ClaudeReplayFixtures.integration.test.ts`,
`CodexReplayFixtures.integration.test.ts` and `AcpRegistryReplayFixtures…`
run the real adapter and orchestration, with only the transport replayed.
The method is in `docs/orchestration-v2/testing-strategy.md`, and the
recorder is `testkit/CommandOutputRecorder.ts`.

**For us:** these transcripts become replay input for our own adapters' tests.
Keep T3 Code's MIT notice next to any file we copy.

## 3. The routes to the Harnesses

- **Claude Code:** the official Claude Agent SDK. It exists for TypeScript
  and Python, not Rust.
- **Codex:** its app-server, which is JSON-RPC over stdio. Codex is written
  in Rust, so our engine speaks it natively.
- **Everyone else:** ACP, with a small per-agent hook only where the agent
  goes beyond the specification.

**What ACP lacks, per their docs:**

- conversation rollback: the turn after a rollback starts a fresh session;
- approvals that survive a restart;
- portable subagent lineage;
- defined usage figures;
- HTTP MCP servers on some agents. T3 Code injects its MCP over a stdio
  bridge instead.

Our first step uses ACP. The native adapters for Claude Code and Codex
follow when one of these gaps blocks a user (ADR 0002, decision 10).
