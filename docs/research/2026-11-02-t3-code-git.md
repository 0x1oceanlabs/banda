## 1. What makes it good

1. **One button that knows what comes next.** The main git button reads
   the status and offers the one next step: `Commit`, `Commit & push`,
   `Commit, push & PR`, `Push`, `Push & create PR`, `Create PR`, `Pull`,
   `Publish repository`, `Initialize Git` (11 rules in order, a pure
   function, `GitActionsControl.logic.ts:177-327`). It runs the whole
   chain at once, with a message a model writes and every file. The
   commit dialog (pick files, write the message, "Commit on new branch")
   is behind the `▾` only. A disabled button says why on hover ("Branch is
   up to date. No action needed.").
2. **Feedback stays where you clicked.** Progress is in the button: the
   step ("Generating commit message...", "Committing...", "Running
   pre-commit...", with the hook's last line, "Pushing...", "Creating pull
   request..."), a timer, then a ✓ for 10 seconds. Only errors are toasts,
   and they stay until dismissed.
3. **One safety net, on the default branch only.** Push or PR on `main`
   asks: `Abort`, `Push to main`, or `Check out feature branch & continue`,
   where a model names the branch (`feature/<words>`).
4. **The Diff compares what you ask.** One scope menu: **Changes** (the
   branch and the work tree against where it left the default branch; the
   default), **Uncommitted**, **Latest turn**, **Turn ▸ N**, **Commits ▸
   …**; for Changes a `head → base` picker ("Automatic" or any ref). The
   chosen scope is kept per thread.
5. **A real diff view.** `@pierre/diffs` 1.6 (Apache-2.0, on Shiki):
   stacked or split, wrap, sticky 32 px file headers, line numbers,
   "expand context" that loads the whole file, virtualised, highlighted in
   workers, find (Mod+F). Files start folded; a click on the header folds,
   a click on the path opens the file. The file tree (`@pierre/trees`) is
   on the right, off by default, and a click scrolls the diff to the file.
6. **Big diffs stay fast.** The server caps a patch at 120 KB and a file at
   1 MiB, but always gives every file's `+N −M` (`--numstat`). Past the cap,
   every file still has its header and counts, and patches load four at a
   time as one scrolls: "This preview exceeds the size limit. Changes
   shown are incomplete. Totals include all changes."
7. **Comments go to the Agent.** Select lines, the gutter `+`, "Add a
   comment…", `⌘/Ctrl Enter`: a chip `DiffPanel.tsx L120 to L134` lands in
   the composer, and the message carries the file, the range, the scope,
   the comment and the hunk. Nothing is stored on a server.
8. **Quiet.** No headings, no fills at rest, emerald and red mixed into the
   background (rows 50 % / 70 %, numbers stronger), modified files in a
   muted blue "so the common case stays quiet".
9. **It never fights your git.** Every git call sets
   `GIT_OPTIONAL_LOCKS=0`, so a status never takes `index.lock`; untracked
   files are diffed through a copied index (`GIT_INDEX_FILE` and
   `add --intent-to-add`), so the real index is never touched; status
   waits while `index.lock` exists; at most 8 short git processes at once;
   git's own error text is classified, not shown raw (it can hold
   credentials).

## 2. Its backend in one page

- **Runner:** the `git` program only, one runner: env, a 30 s time limit
  (push none, commit 10 min), capped output, a semaphore of 8.
- **Diff:** `git diff --find-renames --no-color --no-ext-diff --no-textconv
  --src-prefix=a/ --dst-prefix=b/ --minimal [--ignore-all-space]`, the
  patch as text plus `--numstat -z` for the counts. Uncommitted is the work
  tree against `HEAD`; Changes the work tree against `merge-base <base>
  HEAD`.
- **Automatic base:** T3's own `branch.<b>.t3-merge-base` config, then
  `refs/remotes/origin/HEAD`, then `main`, then `master`.
- **Status:** `git status --porcelain=2 --branch -z --no-ahead-behind` and
  `git diff-index -M --numstat -z HEAD`. No file watcher: it is read again
  when a turn ends, after each git action of T3's, on request, and while a
  Pane follows, a `git fetch --no-tags` every 30 s for ahead and behind.
- **Refs:** one `git for-each-ref` over `refs/heads` and `refs/remotes` by
  commit date. Switching is `git checkout <ref> --`, no stash: git's
  refusal shows as a toast.
- **The chain:** `git add -A` (or the files picked), a message from a text
  model (Codex `gpt-6-luna`, low effort) on the staged patch capped at
  49 KB, `git commit`, `git push <remote> HEAD:refs/heads/<b>` with the
  upstream written by T3, then the PR through GitHub's REST API. Progress
  streams as events, hook output through `GIT_TRACE2_EVENT`.
- **Turns:** a checkpoint after each turn, a commit of the whole work tree
  made through a temp index (`add -A`, `write-tree`, `commit-tree -p
  HEAD`, `update-ref refs/t3/…/ordinal/<n>`), never touching the Person's
  index, HEAD or branch. "Turn N" diffs checkpoint N−1 against N, without
  the files the Agent did not write. T3 never deletes them when a thread
  goes.

## 3. Where Banda stands

- **The diff view** is Banda's own, about 500 lines: one stacked column,
  no line numbers, no highlighting, no folding, no tree, each file in a
  box of at most 320 px (`app/ui/src/components/diff.tsx`), a Myers line
  diff that gives up past 1000 edits (`modules/agents/pane/src/diff.ts`).
  A turn's changes come from its tool calls, so a change made through the
  shell (`sed`, a code generator, `git checkout`) is not in them.
- **Shiki** 4 is there already (the composer's code), and so are
  `react-resizable-panels`, dialogs, menus and `PaneHeader`; a combobox,
  a tooltip and a toggle group are not.
- **Colours:** `added` and `removed` are the Omarchy palette's green and
  red (`look/src/tokens.rs:47-48`).
- **Git:** only `git ls-files` for `@`.

## 4. For the UX talk

What is worth taking whole, and what Banda's Panes and Harnesses change:

1. **The renderer:** `@pierre/diffs` and `@pierre/trees`, as T3 does,
   instead of growing Banda's own view.
2. **Turn from checkpoints**, as T3 does, so a turn shows everything the
   Agent changed, the shell's work too, and Edit from here can later put
   files back. ADR 0034 says tool calls; checkpoints need a git Space, so
   tool calls stay for a Space that is no repository.
3. **The message a model writes:** T3 calls a text model (Codex). Banda has
   Harnesses, not a text model; the message can come from a Harness's
   one-shot run, or be the Person's to write at first.
4. **Where the button lives:** T3 has a card over the chat. Banda has
   `git.space`, a Pane; the status could also sit in the Thread's header
   or the top bar (ADR 0024 kept a place for "the branch and its pull
   request").
5. **Keys:** T3's Mod+D (the Diff) and Mod+Shift+G (the branch) against
   `keys.toml`.
